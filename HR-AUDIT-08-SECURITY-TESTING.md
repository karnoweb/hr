# 8. Security & Authorization Audit / 9. Test Strategy Audit

Part of the Karnoweb HR audit. See `HR-AUDIT.md` for the index.

## 8. Security & Authorization

The package assumes almost nothing about authentication/authorization by design (it's a domain package, not an app), which is architecturally correct — **but** the few places it *does* touch `auth()` directly do so inconsistently and without any accompanying ownership check, which is the actual problem, not the general absence of an auth layer.

| Area | Risk | Severity | Required Solution |
|---|---|---|---|
| `DocumentService::approve()` (`src/Services/DocumentService.php:99-120`) | **IDOR.** The method accepts a `DocumentApproval $approval` model instance and only checks `$approval->status === Pending`. It never checks whether the current actor (`auth()->id()`) equals `$approval->assigned_to`. Any caller who can obtain or guess a pending approval's ID (e.g., via a predictable route parameter in the consuming app) can approve a step assigned to someone else — the package provides no defense against this at all; the entire burden is silently pushed onto the integrating application with no documentation saying so. | P0 | Add an explicit ownership check inside `approve()`/`reject()` (or require the caller to pass an actor id and verify it against `assigned_to`) and throw a dedicated `UnauthorizedApprovalException` on mismatch. Document clearly that the package does not do this by default only if that's the intentional design — but given the method's whole purpose is "act on an approval", the check belongs here. |
| `DocumentService::approve()`/`reject()`/`recordHistory()` — direct `auth()->id()` calls (`src/Services/DocumentService.php:174, 206`) | **Global/static dependency + silent data loss in non-HTTP contexts.** Calling these methods from an Artisan command, a queued job, or a test without an authenticated web session silently records `NULL` for `approved_by`/`user_id` — no exception, no warning. This also makes the service impossible to unit-test for the "who approved this" behavior without faking a global auth state (`Auth::login()` in tests), which actively discourages writing tests. | P0 | Accept the actor as an explicit parameter (e.g., `approve(DocumentApproval $approval, ?string $comment = null, $actorId = null)`, defaulting to `auth()->id()` only at the call site the *consuming app* controls, not buried inside the package). |
| `EmployeeService::createForUser()` (`src/Services/EmployeeService.php:29-55`) | No check that the calling context is authorized to create an HR record for the given `$user` — by itself this may be intentional (the package defers all authorization to the host app's controllers/policies), but this is **undocumented**, so an integrator has no signal that they must add this check themselves. | P1 | Document explicitly (in `docs/USAGE.md` and class-level docblocks) that authorization is entirely the caller's responsibility for every service method; this is a documentation gap, not necessarily a code gap, given the package's intended role. |
| Branch scoping (`Department`, `Position`, `Shift`, `Employee`, `HrDocument`, `Workflow`, etc. — all have a `branch_id` column) | **Could a caller access another branch's employee/department/etc.?** Yes, trivially — every model's default query has zero branch filtering; `scopeForBranch()` helpers exist on several models but are opt-in, not applied automatically anywhere. `Employee::find($id)` returns any employee regardless of branch. | P1 (documented risk, likely intentional architecture) | This is defensible as a deliberate design choice (the package is branch-agnostic and expects the host app to apply branch scoping via global scopes/policies) — but it must be **stated explicitly** as a required integration step, since right now nothing in the docs says "you must add branch-scoping middleware/policies yourself before exposing this to end users." |
| Payroll period mutation (future `PayrollService`, not yet implemented) | **Could a caller modify a closed/locked payroll period?** Cannot be assessed on real code yet since no `PayrollService` exists — flagging as a **forward-looking requirement**: `PayrollPeriodStatus::canEdit()` exists as a helper (`src/Enums/PayrollPeriodStatus.php:48-51`) and correctly returns `false` for `Approved`/`Paid`/`Locked`, but since nothing calls it yet, there is currently no enforcement of any kind once the calculation engine is written unless this helper is actually wired in. | P0 (for the upcoming implementation) | Every future `PayrollService` mutation method must call `$period->status->canEdit()` (or equivalent) and throw before writing, exactly the way `HrDocument::ensureEditable()` already does for documents — reuse that pattern. |
| Approval step assignment resolution (future workflow fix) | **Could a caller approve an approval step assigned to someone else?** Directly related to the IDOR finding above — once `approver_type` resolution is implemented (Section 3/Workflow), the resolution logic itself must not be exploitable (e.g., a `Custom` approver type resolved from caller-supplied input must not let the caller name themselves as the approver). | P0 (for the upcoming implementation) | Ensure approver resolution for every `ApproverType` is derived from trusted, server-side data (the document's employee's actual department/position at submit time), never from caller-supplied parameters. |
| Document locking (`HrDocument.locked_at`) | **Could a caller modify a document after locking?** `canEdit()`/`ensureEditable()` only check `status === Draft` (`src/Enums/DocumentStatus.php:35-38`); they never check `locked_at`. A document can be `Approved` but not yet past its `lock_delay_hours` window — but since `canEdit()` already returns `false` for anything other than `Draft`, `locked_at` is actually redundant/unused for edit-blocking today (it appears intended for a *future* distinct purpose, e.g., blocking cancellation or reversal, that doesn't exist yet). Not a live vulnerability today, but a dead/confusing field that could mislead a future implementer into thinking edit-blocking already accounts for the lock delay. | P2 | Document the intended purpose of `locked_at` explicitly, or wire `ensureEditable()`/a new `ensureUnlocked()` to check it once a concrete "post-approval but pre-lock, still reversible" workflow is designed. |
| Mass-assignment surfaces (`$fillable` arrays across all models) | No model exposes obviously dangerous mass-assignable fields (e.g., `status`, `is_current`, `approved_by` are generally excluded from `$fillable` where it matters — spot-checked `HrDocument`, `Employee`, `Loan`) — **no finding**. | — | No action needed. |
| SQL injection surface | All queries use the query builder/Eloquent with parameter binding; no raw string interpolation into SQL found anywhere in `src/`. **No finding.** | — | No action needed. |

## 9. Testing Gap Analysis

**No tests exist at all** — `tests/` directory is absent despite being declared in `composer.json`'s `autoload-dev` (`composer.json:28-32`) and despite `phpunit/phpunit` + `orchestra/testbench` being physically present in `vendor/` per `composer.lock`'s `packages-dev` section. The table below lists what's needed per domain, not a percentage.

| Domain | Existing Tests | Missing Critical Scenarios | Priority |
|---|---|---|---|
| Package bootstrap | None | Service provider registers `hr` singleton and merges config; facade resolves; migrations load and run cleanly against a fresh Testbench SQLite/MySQL DB; config publishing works. (Architecture: **Feature**) | P0 |
| Employee | None | Happy path: `createForUser()` creates a linked employee with auto-generated code. Validation failure: wrong `$user` class throws. Boundary: creating two employees "simultaneously" (two DB connections/processes) never produces a duplicate `employee_code` (**Concurrency**). Uniqueness: duplicate `national_id` behavior once constrained. State transitions: termination/reactivation once implemented. (Unit for code-format logic, **Feature** for `createForUser`, **Concurrency** for the race test) | P0 |
| Organization (Department/Position) | None | Tree consistency after create/move (`updatePath()`). Cycle prevention. Multi-branch: same `code` in two branches succeeds once fixed (currently would need to assert today's *failure*, then flip the assertion once fixed). Soft-delete of a parent with children — documents current (broken) behavior as a regression baseline before fixing. (**Unit** for path math, **Feature**/**Database** for constraints) | P1 |
| Contract | None | Everything — there is no service to test yet, so tests should start with schema-level expectations (e.g., a DB test asserting the "one active contract" invariant once implemented) and grow alongside the future `ContractService`. (**Database**, then **Feature** once built) | P1 |

Sequential vs. parallel gating once implemented. Condition evaluation once implemented. Timeout/escalation once implemented. | P0 |

### Suggested test-type distribution (once a suite exists)

- **Unit**: enum helpers (`label()`, `color()`, `rate()`, `canEdit()`/`canApprove()`/`canCalculate()`), pure calculation functions (day-counting, bracket application, overtime rate math) — fast, no DB.
- **Feature**: every service method's happy path + documented failure modes, using Testbench with an in-memory/SQLite DB.
- **Database**: every unique/foreign-key constraint asserted directly (insert two conflicting rows, expect a specific exception) — these double as living documentation of Section 4/5's findings and should be written **before** any fixes, as regression baselines.
- **Concurrency**: anything in Section 6's table — realistically simulated via either genuinely parallel DB connections/processes in a dedicated slower test group, or via deliberately interleaving two service calls around a manually-controlled lock/transaction in a single test (the more common, cheaper approach for this kind of package).
- **Integration**: the accounting-boundary "works standalone" test, and a full payroll-period lifecycle test spanning multiple domains (attendance + leave + overtime + salary + loan → payroll record).
- **Architecture**: none recommended at this scale — introducing an architecture-testing tool (e.g., `pestphp/pest-plugin-arch` or similar) would be reasonable *once* the Domain/Actions/Rules split from Section 10 is adopted, to enforce layer boundaries, but is over-engineering to introduce before that split exists.
