# 6. Concurrency & Idempotency Audit / 7. Transaction Boundary Audit

Part of the Karnoweb HR audit. See `HR-AUDIT.md` for the index.

## 6. Concurrency & Idempotency

| Operation | Risk | Scenario | Required Solution | Priority |
|---|---|---|---|---|
| Employee code generation (`EmployeeService::generateEmployeeCode()`, `src/Services/EmployeeService.php:109-145`) | Classic read-then-compute-then-insert race; the pattern `orderByDesc('employee_code')->value(...)` then `+1` has no lock and no transaction. | Two `createForUser()` calls fire within the same request-handling window (two HR admins onboarding different new hires at once). Both read the same "last code" (e.g. `1403-0007`), both compute `1403-0008`, both call `Employee::create()`. The DB's unique constraint on `employee_code` catches the collision, but as an **unhandled `QueryException`** surfacing to whichever request loses the race — the second hire operation fails outright instead of transparently retrying. | Introduce a dedicated `hr_sequences` table (`scope` string, `last_value` unsigned int) and a small `SequenceGenerator` service that does `DB::transaction(fn () => Sequence::query()->where('scope', $scope)->lockForUpdate()->increment('last_value'))`, returning the new value atomically. `generateEmployeeCode()` calls this instead of `orderByDesc(...)->value(...)`. | P0 |
| Document number generation (`HrDocument::generateDocumentNumber()`, `src/Models/HrDocument.php:98-110`) | The `lockForUpdate()` is real, but it protects a `count()` read that happens **inside** a transaction that commits (releasing the lock) *before* the actual `INSERT` of the document row happens (that `INSERT` occurs afterward, in Eloquent's normal `save()` flow, driven by the `creating` event's return value being assigned to an attribute — not inside the locked transaction at all). | Two `hire` documents are created for two employees within the same second. Both transactions independently lock, count existing `hire` documents for the current year (say, 4), commit (releasing the lock), and both compute `sequence = 5`. Both then attempt `INSERT ... document_number = 'HIR-2026-0005'`; the unique constraint on `document_number` causes the second `INSERT` to throw. | Same fix pattern as employee code: a `hr_sequences` row scoped by `(type, year)` (and `branch_id` if branch-scoped numbering is desired), incremented atomically inside a single transaction that also performs (or is immediately followed, within the same transaction, by) the actual document `INSERT` — i.e. move sequence allocation and the row insert into one transaction, not two independent ones. | P0 |
| Workflow approval-step creation for non-`user` approver types (`DocumentService::submit()`, `src/Services/DocumentService.php:76-84`) | Not a race condition per se — a deterministic crash — but included here because it manifests as an *idempotency* failure: a `submit()` call that fails partway through the approval-creation loop leaves some `DocumentApproval` rows created and others not, and the document is already `Pending` (see Transaction Boundary table below), so retrying `submit()` is not safe (it is not idempotent; it would attempt to create a second, duplicate, set of approvals for the steps that already got one). | An HR admin submits a `position_change` document whose workflow has 3 steps: `user` (approver_id=42), `department_head` (approver_id=null), `user` (approver_id=7). Step 1's approval inserts fine. Step 2's insert throws (NOT NULL violation on `assigned_to`). The admin retries `submit()` — but the document is already `Pending` and `ensureEditable()` will now throw `DocumentLockedException` since `Pending` isn't `Draft`; the document is stuck with exactly one approval row forever, unrecoverable without direct DB intervention. | Resolve every step's concrete approver *before* any writes happen (a pure, side-effect-free resolution pass over all steps that either succeeds for all steps or throws a clear domain exception without having written anything), then perform the status update + all approval inserts inside a single transaction (see Transaction table). | P0 |
| `DocumentService::approve()` / `reject()` (`src/Services/DocumentService.php:99-151`) | Read-then-write on `DocumentApproval.status` with no `lockForUpdate()`; the guard is only "is this specific approval still pending", not "is the parent document still pending". | Two approvers for two different steps of the same document call `approve()`/`reject()` within milliseconds of each other. If one calls `reject()` (which directly sets `documents.status = Rejected`) while the other's `approve()` is mid-flight, the other's `approve()` will still succeed (it never checks the document's current status) and then call `advanceDocumentStatusIfComplete()`, which may re-read "no pending approvals left" and set the document back to `Approved`, **overwriting the rejection**. | `approve()`/`reject()` must, inside a transaction, `lockForUpdate()` the parent `HrDocument` row first, verify `document.status === Pending` before proceeding, and only then read/write the approval row and (if applicable) the document's aggregate status. | P0 |
| Leave balance check-and-decrement (not yet implemented, but must be designed correctly from the start) | Textbook check-then-act race once `LeaveService` gains real validation: "read remaining balance, if sufficient create request" and, separately in the future, "on approval, decrement balance" are both check-then-write without a lock. | Two leave requests for the same employee/year/type are submitted almost simultaneously, each for an amount within the remaining balance individually but not combined. Both read the same "remaining = 5 days" before either commits its request, both pass validation, both get created — total requested (e.g., 4 + 4 = 8) exceeds the actual balance of 5. | Wrap the balance check + request creation in a transaction that `lockForUpdate()`s the relevant `LeaveBalance` row for the duration of the check-and-create. | P0 |
| Loan eligibility (`max_active_loans`, `max_percentage_of_salary`) — not yet implemented | Same check-then-insert race pattern as leave balance, once written. | Two loan requests submitted concurrently for an employee who is exactly at the `max_active_loans` boundary (e.g., 1 active loan, limit 2) — both read "1 active loan, under limit", both get approved and created, employee ends up with 3 active loans. | Lock the employee's loan rows (`SELECT ... FOR UPDATE` on active loans for that employee, or lock a per-employee "loan eligibility" row) for the duration of the eligibility check + insert, inside one transaction. | P1 |
| Payroll period calculation (not yet implemented) | The single most important idempotency requirement in the whole package: "calculate this period" must be safe to run once, and safe to **re-run** (recalculation after a correction) without double-applying earnings/deductions or leaving orphaned `PayrollRecord` rows from a prior, different calculation. | An admin triggers "calculate payroll" for March; the job runs long enough that the admin (thinking it hung) clicks "calculate" again. Without idempotency, this either duplicates work, produces two conflicting sets of numbers, or (if implemented via blind `create()` calls) violates the existing `unique(['payroll_period_id','employee_id'])` constraint non-gracefully rather than treating it as "recalculate = replace". | Design the calculator so "calculate" is `updateOrCreate` per `(payroll_period_id, employee_id)` inside a transaction per employee (or per period, sized appropriately), gated by `PayrollPeriodStatus::canCalculate()` (already exists as a helper, unused today) checked under a lock on the `PayrollPeriod` row itself so two concurrent "calculate" triggers for the same period can't both proceed. | P0 |
| `Department::updatePath()` (`src/Models/Department.php:70-78`) | Recursive, unlocked, non-transactional cascade of updates across a subtree. | Two concurrent department moves affecting overlapping subtrees (e.g., moving department A under B while also moving B's parent) interleave their per-node updates with no lock, producing an inconsistent `path`/`level` for some nodes (whichever write lands last, per-node, wins — not an atomic "the whole subtree" operation). | Wrap the entire cascade (from the moved node down through all descendants) in a single transaction; consider locking the root of the affected subtree for the duration. | P2 |
| `EmployeePosition`/`EmployeeSalary`/`Contract` "close old, open new" (future service methods) | Not yet implemented, but flagged pre-emptively since it's the same pattern as the leave-balance race: reading the "current" row, updating its `end_date`/`is_current`, and inserting the new "current" row must be one atomic unit. | Two near-simultaneous "give this employee a raise" operations (e.g., a manual correction racing an approved `salary_change` document being processed by a scheduled job) both read the same "current" salary row, both flip it to non-current, both insert a new current row — resulting in either two new "current" rows (if the DB-level fix from Section 5 isn't in place) or, if it is, one of the two operations failing with a unique-constraint violation it doesn't know how to recover from gracefully. | Lock the employee's "current" row (`lockForUpdate()`) for the duration of the close-old/open-new sequence, inside a transaction, for every domain that has this pattern (Salary, Position, Contract, Shift Assignment). | P0 |

## 7. Transaction Boundaries

| Operation | Current State | Required Boundary | Priority |
|---|---|---|---|
| Employee creation (`EmployeeService::createForUser()`) | **Atomic** in the sense that it's a single `Employee::create()` call — but employee-code generation happens *before* that call, as a separate, unlocked read (see Concurrency table); the overall operation is not wrapped in a transaction that also covers a future "assign initial position/contract/salary" step if `createForUser()` is ever extended to do more than just the bare `Employee` row. | Keep the current single-insert as-is once the sequence-generation race is fixed at the generator level; if creation is later extended to also create an initial `Contract`/`EmployeePosition`/`EmployeeSalary` in one call (a plausible future "onboarding" convenience method), that combined operation must be wrapped in `DB::transaction()`. | P1 (for the future extension; today's single-insert is fine on its own) |
| Document creation (`DocumentService::create()`) | **Atomic** — single `HrDocument::create()` call, no other writes. | No change needed. | — |
| Document submission (`DocumentService::submit()`, `src/Services/DocumentService.php:65-88`) | **Unsafe.** Three separate, unwrapped writes: (1) `$document->update(['status' => Pending])`, (2) a loop of N `DocumentApproval::create()` calls, (3) `recordHistory()`'s `DocumentHistory::create()`. A failure after step 1 (e.g., an approver-resolution error for a `department_head` step, or any DB error mid-loop) leaves the document `Pending` with zero or a partial set of approvals — and, per the Concurrency table, **not retriable**, since the document is no longer `Draft`. | Wrap the entire method body in `DB::transaction()`. Additionally, resolve every step's approver *before* entering the transaction (a separate, pure, read-only pass) so the transaction itself is guaranteed to only contain valid inserts and doesn't need to roll back due to a resolution failure it could have caught earlier. | P0 |
| Document approval (`DocumentService::approve()`) | **Unsafe** — see Concurrency table: no lock on the parent document, and the approval-row update plus `advanceDocumentStatusIfComplete()`'s subsequent reads/writes (pending-count check, rejected-count check, document status update, optional lock-timestamp update, history insert) are 2-5 separate unwrapped statements. | Wrap in `DB::transaction()` with `lockForUpdate()` on the parent `HrDocument` row acquired first, then the approval update, then the aggregate-status logic, all inside the same transaction. | P0 |
| Document rejection (`DocumentService::reject()`) | **Unsafe** — same issue: approval update, document status update, and history insert are 3 separate unwrapped statements; also does not mark sibling pending approvals as `Skipped` (a data-consistency gap, not just a transaction-boundary one — see Domain Audit / Workflow). | Wrap in a transaction with the same document-row lock as `approve()`; additionally, within that same transaction, update any other still-`Pending` `DocumentApproval` rows for the document to `Skipped`. | P0 |
| Leave request (`LeaveService::request()`) | **Atomic** today only because it does nothing but one `LeaveRequest::create()` — but this will become **unsafe** the moment balance validation/decrement is added unless designed with a transaction + lock from the start (see Concurrency table). | Design the eventual "validate balance, create request" as one transaction with a `lockForUpdate()` on the relevant `LeaveBalance` row. | P0 (for the upcoming implementation) |
| Leave approval (not yet implemented) | N/A — doesn't exist. | Must be one transaction covering: leave-request status update, `LeaveBalance.used_days`/`remaining_days` decrement, and (if applicable) attendance-record creation for the leave dates. | P0 (for the upcoming implementation) |
| Salary change (not yet implemented) | N/A — doesn't exist as a service operation (only raw `EmployeeSalary::create()` per docs). | Must be one transaction covering: closing out the previous "current" salary row (and its `EmployeeSalaryItem` rows if replaced) and inserting the new current row, under a lock on the employee's current-salary state (see Concurrency table). | P0 (for the upcoming implementation) |
| Payroll calculation (not yet implemented) | N/A — doesn't exist. | Per-employee: one transaction per `PayrollRecord` `updateOrCreate`, gated by a period-level lock preventing two concurrent "calculate" runs for the same period; per-period: the period's status transition (`Draft/Calculated → Calculating → Calculated`) should itself be set/cleared transactionally around the whole batch so a crash mid-calculation leaves the period visibly `Calculating` (recoverable/retriable) rather than silently `Calculated` with only half the employees processed. | P0 (for the upcoming implementation) |
| Payroll closing/locking (not yet implemented) | N/A — doesn't exist, though `PayrollPeriodStatus::canApprove()`/`canEdit()` helpers already exist unused. | One transaction: verify `canApprove()`, set period status + `approved_at`/`approved_by`, and (once the accounting-event boundary exists) dispatch the "payroll approved" event — the event dispatch should happen **after** the transaction commits (e.g., via `DB::afterCommit()` or an Eloquent "committed" hook), not inside it, so listeners never observe an uncommitted period. | P0 (for the upcoming implementation) |
| Loan creation (not yet implemented) | N/A — doesn't exist as a service operation. | One transaction: eligibility check (locked, per Concurrency table) + `Loan::create()` + initial `LoanPayment` schedule generation (N rows) — all four schedule considerations should fail together or succeed together. | P1 (for the upcoming implementation) |
| Loan repayment (not yet implemented) | N/A. | One transaction: `LoanPayment` status update + `Loan.remaining_amount`/`remaining_installments` decrement — these two must never be updated independently (today's schema has no trigger/generated-column tying them together, so this **must** be enforced in the service layer). | P0 (for the upcoming implementation) |
| Position change (`EmployeeService::assignPosition()`) | **Partially atomic.** The single `EmployeePosition::create()` call is atomic on its own, but the *missing* "close out the previous current position" step means the operation as a whole (once that step is added) must become a single transaction, not two independent writes. | Wrap "close previous current `EmployeePosition` row (set `end_date`) + insert new one" in one transaction with a lock on the employee's current-position state. | P0 (for the upcoming implementation) |
