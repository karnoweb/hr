# 10. Architecture Recommendations / 11. Configuration Audit / 12. Public API Audit / 13. Performance Audit / 14. Package & Release Quality

Part of the Karnoweb HR audit. See `HR-AUDIT.md` for the index.

## 10. Architecture Recommendations

The current `Models / Services / Facade` shape is **not fundamentally wrong** for a package this size. The recommendation is **not** a rewrite into a full DDD layering — it's targeted, evidence-driven additions where a specific, real complexity problem exists today.

### Keep (already correct — do not touch)

- **The domain boundary/module list itself** (Employee, Organization, Contract, Attendance, Leave, Overtime, Salary, Payroll, Loan, Workflow, Documents) — this vocabulary is coherent and matches how a real HR/payroll system is naturally decomposed. No renaming or re-scoping needed.
- **Backed enums with `label()`/`color()`** and the bilingual translation file pattern (`resources/lang/{en,fa}/enums.php`) — simple, working, appropriately low-tech for what it does.
- **The `Model → Table` prefix mechanism** (`BaseModel::getTable()`, `src/Models/BaseModel.php`) — a small, self-contained solution to a real requirement (configurable table prefix), correctly implemented.
- **Polymorphic `employable`** on `Employee` — correctly decouples the package from any specific `User` implementation; this is exactly the right amount of abstraction (one relation, not a whole "identity provider" interface).
- **Structure/Item and Period/Record pairing** (`SalaryStructure`+`SalaryStructureItem`, `PayrollPeriod`+`PayrollRecord`, `Workflow`+`WorkflowStep`) — normalized correctly; no schema redesign needed here.
- **Avoiding a repository layer, avoiding DTOs for every model** — the package correctly does *not* over-engineer the parts it has built. This restraint should be preserved as new services are added: **do not** introduce a generic repository interface for every model "for consistency" — Eloquent models are the right level of abstraction for a package like this.

### Improve (incremental, targeted)

- **`Hr` facade / service resolution** (`src/Hr.php:22-47`): replace `new EmployeeService` with container resolution (`$this->app->make(EmployeeService::class)`, registered as `singleton` or `scoped` in `HrServiceProvider::register()`). Concrete problem this solves: as soon as a future `PayrollService` needs constructor-injected `TaxCalculator`/`InsuranceCalculator` dependencies (see below), manual `new`-ing breaks down; container resolution solves this with zero added abstraction (no interfaces required, just `$this->app->singleton(PayrollService::class)`).
- **Calculators, not a generic "Rules engine"**: the concrete, real complexity that justifies a new abstraction is calculation logic that (a) has multiple inputs from different domains and (b) needs to be independently unit-testable without a database. This applies to exactly four things today: **`TaxCalculator`**, **`InsuranceCalculator`**, **`OvertimeCalculator`**, **`PayrollCalculator`** (which composes the other three plus salary/leave/attendance data). Each should be a plain, stateless class taking primitive/value inputs and returning primitive/value outputs — no interfaces needed yet (there is exactly one implementation of each; introducing a `TaxCalculatorInterface` today would be speculative, not justified by current complexity — revisit only if/when a second tax regime is genuinely required).
- **A small number of domain exceptions**, following the existing `DocumentLockedException` pattern (`src/Exceptions/DocumentLockedException.php`) — e.g. `InsufficientLeaveBalanceException`, `DuplicateActiveContractException`, `UnresolvableApproverException`, `PayrollPeriodLockedException`. This is a natural, low-cost extension of a pattern that already exists and already works well; it directly solves the "unhandled `QueryException` bubbles up to the caller" problem seen repeatedly in this audit (numbering race, workflow crash, etc.) by giving each failure mode a specific, catchable type.
- **One event per cross-domain boundary that genuinely needs to be decoupled** — concretely: a `PayrollPeriodApproved` event (carrying period totals) is the *only* event that's currently justified, because it's the one real integration seam with an external system (Accounting) that must not be a hard dependency. Do **not** add an event for every CRUD operation (e.g., "EmployeeCreated", "LeaveRequested") unless a second, real consumer for that specific event is already identified — speculative eventing adds indirection with no present payoff.
- **A thin "sequence" service** (`hr_sequences` table + `SequenceGenerator`, see Concurrency file) — solves two concrete, already-identified bugs (employee code, document number) with one small, reusable piece of infrastructure, rather than two bespoke fixes.

### Redesign (current architecture is fundamentally insufficient — needs new code, not a patch)

- **Workflow "engine"**: today's `DocumentService::submit()` loop is a fundamentally wrong shape for what `Workflow`/`WorkflowStep`'s schema promises (conditional steps, required/optional, sequential ordering, approver-type resolution, timeouts). This isn't a bug-fix-sized change; it needs a dedicated `WorkflowEngine`/`ApprovalOrchestrator` service that: resolves approvers per `ApproverType` (a small `ApproverResolver` with one method per type — this is the right place for a `match` statement, not an interface-per-type, since there are only 4 fixed types), evaluates `condition` JSON against document data, and decides step activation order (sequential: only activate step N+1's approvals once step N's required approvals are done; parallel: activate all at once — the `Workflow`/`WorkflowStep` schema should probably gain an explicit `execution_mode` distinguishing these rather than inferring it, since today it's silently always-parallel).
- **Payroll calculation**: needs to be designed and built as a pipeline from scratch (Attendance → Leave → Overtime → Salary/Allowances/Deductions → Insurance → Tax → Loans → Net), not incrementally patched onto existing schema. This is the single largest piece of net-new work in the package.
- **Insurance & Tax**: currently pure configuration with no domain model at all. These need, at minimum, a small versioned-rate concept (see Configuration Audit below) before any calculator can be written — this is a data-modeling gap, not just a missing service.

**Overall conclusion on configuration:** the file is well-organized and the *shape* of every section is reasonable. The real problems are (1) roughly half of it is currently inert (read by nothing), and (2) `insurance.*`/`tax.*`/`payroll.minimum_wage` mix genuine regulatory figures with no versioning into a plain static config array, which is a real liability for a payroll system that will eventually need to recalculate historical periods correctly across a fiscal-year rate change. Neither problem requires a rewrite — (1) is fixed simply by building the services that read these keys (tracked in the checklist), and (2) requires one new small "versioned rate" concept, not a general "everything becomes a database policy" overhaul (most of the file is fine as static config).

## 12. Public API Audit

| Surface | Should be considered public? | Stability | Notes |
|---|---|---|---|
| `Hr` facade (`Karnoweb\Hr\Facades\Hr`) | Yes — this is the documented, intended entry point (`README.md`, `docs/USAGE.md`) | **Unstable** | Its surface will necessarily grow a lot (payroll, insurance, tax, workflow, loan sub-services) as the checklist is implemented; every new sub-service accessor is a new public method, so semantic versioning discipline matters immediately (see Section 14). |
| `Hr::config()` | Yes | Stable | Simple passthrough to `config('hr.*')`; low risk of breaking changes. |
| `Hr::employees()` / `EmployeeService` | Yes | **Unstable** — `generateEmployeeCode()`'s signature/behavior will need to change once the sequence-generator fix lands (Section 6); this is a **known, planned breaking change** for a P0 bug fix. | |
| `Hr::leave()` / `LeaveService` | Yes | **Very unstable** — `request()`'s signature will very likely need to grow (it currently accepts a raw, unvalidated `$data` array; adding real validation may require either throwing new exception types from the same method — non-breaking — or restructuring the input shape — potentially breaking). | |
| `Hr::documents()` / `DocumentService` | Yes | **Unstable** — `submit()`, `approve()`, `reject()` will all need signature changes to support actor-parameter passing (Section 8) and workflow-engine integration (Section 10) — both are necessary, planned breaking changes. | |
| Models (`Employee`, `Contract`, `HrDocument`, etc.) under `Karnoweb\Hr\Models` | Yes, but **should be treated as read/query-oriented public API**, not a write API | Mixed — relations and scopes are low-risk to keep stable; direct `Model::create([...])` usage (as shown throughout `docs/USAGE.md`) **bypasses every business rule that services will eventually enforce**, and continuing to document/encourage direct model writes undermines the whole point of building service/calculator layers. | Recommend: once services exist for a domain, update `docs/USAGE.md` to stop showing raw `Model::create()` examples for that domain, to steer integrators toward the safe path. |
| Enums (`Karnoweb\Hr\Enums\*`) | Yes | Stable structurally, but **case additions are non-breaking while case removals/renames are breaking** — flag `ApprovalStatus::Skipped` (currently unused/dead) as a case that must not be silently repurposed once real logic starts assigning it. | |
| `config/hr.php` keys | Yes — every key is part of the public contract once published via `vendor:publish` | **Unstable** for `insurance.*`/`tax.*` specifically, since the versioning fix recommended in Section 11 will change their shape (a single flat array today → likely a list of dated rate entries) — this is a **known future breaking change** worth flagging to consumers now, before they build against the current flat shape. | |
| `DocumentLockedException` | Yes (already public, already used in a public method's `@throws`) | Stable | Good precedent to extend (Section 10). |
| `BaseModel::getTable()` | No — implementation detail | — | Not part of the intended public contract; fine to change freely. |
| Migrations (table/column names) | Yes, implicitly — any queries an integrator writes directly against `hr_*` tables depend on this | **Unstable for the tables flagged in Section 4** (branch-scoped unique constraints, new FK additions, new `hr_sequences` table, potential `current_key` columns) | These are necessary schema changes; should ship as new migrations (never edit existing ones) and be called out prominently in `CHANGELOG.md`. |

**Backward-compatibility risk summary:** the package is currently pre-1.0-in-spirit despite being versioned `13.0.0` (that version number tracks Laravel-version compatibility, not package maturity — worth clarifying in docs, since "v13" reads as "13th major version" to anyone unfamiliar with the Laravel-version-alignment convention). Expect and plan for breaking changes across nearly every service method as the checklist is implemented; this is normal and acceptable, but should be communicated via `CHANGELOG.md` "Changed"/"BREAKING" entries per release, which the file currently does correctly for the one release it documents.

## 13. Performance Audit

Only structurally obvious or measurable-by-inspection issues are reported — no speculative micro-optimization.

| Area | Finding | Risk |
|---|---|---|
| `Department::updatePath()` (`src/Models/Department.php:70-78`) | Recursive, per-node `->update()` call with no eager loading of `children` across the recursion — for a tree of depth *d* and branching factor *b*, this is O(nodes) individual queries. | For typical HR org charts (tens to low hundreds of departments) this is a non-issue; flagging only because it's the one clearly N+1-shaped piece of logic that exists in the codebase today. Not worth optimizing pre-emptively; revisit only if department trees grow large in practice. |
| `EmployeeService::generateEmployeeCode()` (`src/Services/EmployeeService.php:129`) | `orderByDesc('employee_code')->value(...)` on a string column with a `like` prefix filter — without a composite index tuned for this exact query shape (`(employee_code)` alone, which already exists as it's the unique-index column, is likely sufficient), this is fine at current scale; **this finding is really a duplicate of the concurrency issue** (Section 6), not a new performance concern — noted here only to avoid double-fixing it as "add an index" when the real fix (sequence table) makes this query disappear entirely. | Low — superseded by the P0 concurrency fix. |
| `HrDocument::generateDocumentNumber()` (`src/Models/HrDocument.php:103-106`) | `count()` over `where('type', ...)->whereYear('created_at', ...)` — as document volume grows across years, this count scans an ever-larger (though `whereYear`-filtered, so bounded per year) row set; again, superseded by the sequence-table fix, which turns this into an O(1) increment. | Low — superseded by the P0 concurrency fix. |
| Attendance/Payroll reporting (future) | No reporting queries exist yet to audit — flagging pre-emptively: once a payroll calculator reads attendance/leave/overtime per employee per period, doing so via N per-employee queries inside a period-level loop (rather than batched eager-loading per period) would be a real, foreseeable N+1 risk given payroll periods can have hundreds of employees. | Design-time recommendation for the upcoming payroll engine, not a current-code finding. |
| Workflow queries (`Workflow::findForDocument()`, `src/Models/Workflow.php:40-47`) | Single, reasonably indexed query (`document_type` has an index, `...000017...php:25`); no finding. | — |
| Repeated `config()` reads | `config()` is called directly and repeatedly (e.g., `OvertimeType::rate()` on every call) rather than resolved once per request — Laravel's config repository is an in-memory array after boot, so this has effectively zero cost; **not a real performance issue**, mentioned only to note it was checked and dismissed. | None — no action needed. |
| Missing indexes | None found beyond what's already flagged as an *integrity* issue in Section 4 (missing unique indexes) — every foreign key column has a supporting index via `constrained()`'s implicit index, and the explicit composite indexes added (e.g., `employees(status, branch_id)`, `payroll_records(status)`) are sensible for the query patterns the model relations imply. | — |
