# 4. Database Audit & 5. Domain Invariants

Part of the Karnoweb HR audit. See `HR-AUDIT.md` for the index.

## 4. Database Audit

| Area | Finding | Risk | Priority | Proposed Solution |
|---|---|---|---|---|
| `hr_employee_salaries.is_current` | Only a plain composite index `(employee_id, is_current)` exists (`...000022...php:24`); no unique constraint prevents two rows with `is_current=1` for the same employee. | Concurrent salary changes (manual correction + approved `salary_change` document, or two admins) can produce multiple "current" salaries. `Employee::currentSalary()` is a `hasOne` with no `orderBy`, so which one payroll uses becomes non-deterministic — a real risk of paying the wrong salary. | P0 | Add a nullable `current_key` column set to `employee_id` when `is_current=1` and `NULL` otherwise, with a unique index on `current_key` (MySQL-compatible "at most one non-null" pattern). Enforce the flip (`old.current_key=null, new.current_key=employee_id`) inside a single transaction in a new `SalaryService`. |
| `hr_employee_positions` | No unique constraint for "at most one row per employee with `is_primary=1 AND end_date IS NULL`"; only `index(['employee_id','is_primary'])` (non-unique, `...000005...php:25`). | Same class of bug as salary: two "current primary position" rows can coexist, and `currentPosition()`'s `hasOne` ordering by `effective_date` may silently pick the wrong one. | P0 | Same `current_key` pattern as salary, scoped to `is_primary=1 AND end_date IS NULL`. |
| `hr_contracts` | `ContractStatus::Active` has no supporting invariant; no unique/partial-unique constraint prevents two `active` contracts for the same employee. | An employee can end up with two simultaneously "active" contracts (e.g., a renewal created without ending the old one), corrupting anything that reads `currentContract()`. | P0 | Same `current_key` pattern, or introduce an explicit `is_current` boolean column (consistent with `EmployeeSalary`) plus the unique-key trick, maintained by a future `ContractService`. |
| `hr_departments.code`, `hr_positions.code`, `hr_shifts.code`, `hr_shift_patterns.code`, `hr_salary_items.code`, `hr_salary_structures.code` | All declared `unique()` globally (e.g. `...000001...php:17`, `...000002...php:16`, `...000006...php:16`, `...000007...php:16`, `...000020...php:16`, `...000021...php:16`) despite every one of these tables also having a nullable `branch_id` scoping column. | Concrete scenario: Branch A and Branch B both want a department/position/shift/salary-item coded the same way (a completely normal multi-branch pattern, e.g. every branch having a "MORNING" shift code) — the second branch's `INSERT` fails on the global unique constraint. This directly blocks the "Multi-branch behavior" requirement for six different catalog tables. | P0 | Change each `unique('code')` to a composite `unique(['branch_id','code'])`. Requires a migration (not to be written in this phase) and a decision on how a `NULL` `branch_id` (a "global" record) should interact with branch-specific ones — most DBs treat multiple `NULL`s in a unique index as distinct, which is actually the desired behavior here (global codes don't collide with each other by branch, but two *global* records with the same code should still collide) — needs explicit design, not just a mechanical migration change. |
| `hr_employees.employable_type` + `employable_id` | Plain composite index (`...000003...php:41`), not unique. | The same `employable` (e.g., the same `User` row) could be linked to two different `Employee` records with nothing preventing it — a duplicate-identity bug. | P1 | Add `unique(['employable_type','employable_id'])`. |
| `hr_employees.national_id`, `insurance_number` | No uniqueness constraint at all (`...000003...php:22-23`). | Two `Employee` rows can be created for the same real person (same national ID) — a real-world data-integrity hazard for an HR system, and a likely source of duplicate-payroll bugs later. | P1 | Add a conditional-unique approach (nullable columns need a `NULL`-tolerant unique index, which standard unique indexes already provide correctly — every `NULL` is treated as distinct — so a plain `unique('national_id')` is actually safe here and should be added directly). |
| `hr_loan_payments` | No unique constraint on `(loan_id, installment_number)` (`...000024...php`). | Duplicate installment rows for the same loan/number are representable, which would corrupt any "remaining balance = amount − sum(paid payments)" calculation built later. | P1 | Add `unique(['loan_id','installment_number'])`. |
| `hr_*.hr_document_id` columns (on `employee_positions`, `overtime_records`, `leave_requests`, `mission_requests`, `employee_salaries`, `loans`, `payroll_records`) | All plain `unsignedBigInteger`, **no foreign key** to `hr_documents.id`. | These columns can silently point at a non-existent or soft-deleted `HrDocument` with zero DB-level protection; a report or UI that joins on these will get null/broken links with no error. | P2 | Either add `nullable()->constrained('hr_documents')->nullOnDelete()` (requires resolving migration ordering, since several of these tables are created *before* `hr_documents` in the current sequence — `contracts`/`employee_positions` are migration 4/5, `documents` is migration 15) or, if the circular/ordering concern is intentional, document the decision explicitly in a code comment and add app-level validation instead. |
| `hr_documents.branch_id` vs `hr_employees.branch_id` | Independently settable; nothing enforces they match. | A document can be created with a `branch_id` different from its employee's actual branch, which would make branch-scoped workflow resolution (`Workflow::findForDocument()`) apply the wrong branch's workflow. | P1 | Add an app-level (not DB-level — cross-table check constraints aren't portable) validation in `DocumentService::create()`, defaulting/validating `branch_id` against `$employee->branch_id` unless explicitly overridden with a documented reason. |
| `hr_departments` self-FK (`parent_id`) | `nullOnDelete()` (`...000001...php:29-32`) combined with `SoftDeletes` on the model. | The FK action only fires on a **hard** delete; soft-deleting a parent department leaves children's `parent_id` pointing at a row Eloquent's default scope now hides, so `$department->parent` returns `null` and `updatePath()` will misclassify the child as root on its next save, corrupting `path`/`level`. | P1 | Either exclude `Department` from `SoftDeletes` (use `is_active` only, which already exists) or add an app-level guard preventing soft-delete of a department that still has children, and/or make `updatePath()` aware of soft-deleted ancestors via `withTrashed()`. |
| `hr_overtime_records.status`, `hr_loan_payments.status`, `hr_payroll_records.status` | Plain `string(20)` columns with **no corresponding enum cast** in their models (confirmed: `OvertimeRecord`, `LoanPayment`, `PayrollRecord` casts arrays omit `status` entirely, unlike every other status column in the codebase). | Inconsistent typing: arbitrary strings can be written with no validation, and code reading `$record->status` gets a plain string in these three models but a rich enum everywhere else — an easy source of `===` comparison bugs (`'pending' === OvertimeType::...` style mistakes) once these domains get real services. | P2 | Introduce `OvertimeStatus`/`PaymentStatus`/`PayrollRecordStatus` enums (or reuse `PayrollPeriodStatus`/`ApprovalStatus` where semantically identical) and add the missing casts. |
| `hr_leave_requests`, `hr_mission_requests` | No constraint or index supporting overlap detection; only `index(['start_date','end_date'])` on leave requests, nothing comparable on mission requests. | Two overlapping leave/mission requests for the same employee are fully representable at the DB layer; overlap must be enforced entirely in application code (a range-overlap check with row locking), which does not exist yet. | P1 | Not a DB-only fix — needs an app-level overlap check (see Concurrency file) since date-range exclusion constraints aren't portably expressible as a simple unique index across common RDBMS targets for this package. |
| `hr_attendance_records` | `unique(['employee_id','date'])` (`...000010...php:32`). | **This is correct and should be preserved** — flagged here as a positive finding, not a problem. | — | No action needed. |
| `hr_payroll_records` | `unique(['payroll_period_id','employee_id'])` (`...000026...php:56`). | **Correct, DB-enforced, a real strength.** | — | No action needed. |
| `hr_payroll_periods` | `unique(['branch_id','year','month'])` (`...000025...php:31`). | **Correct, DB-enforced.** | — | No action needed. |
| `hr_holidays` | `unique(['branch_id','date'])` (`...000009...php:26`), with `branch_id` nullable for "global" holidays. | A branch can have both a global (`branch_id=NULL`) holiday and its own branch-specific holiday on the same calendar date; `scopeForBranch()`'s `OR` query (`src/Models/Holiday.php:20-22`) will then return two rows for one logical day, and any future working-day calculator that assumes "at most one holiday row per date" will double-count or behave inconsistently. | P2 | Either forbid a branch-specific holiday on a date already covered by a global holiday (app-level check) or design the working-day calculator to explicitly de-duplicate by date from the start. |
| Decimal precision | Monetary columns are consistently `decimal(15,2)` (salaries, loans, payroll) and day/hour counters are `decimal(5,2)` (leave/mission days). | No finding — precision choices are reasonable and consistent across the schema. | — | No action needed. |
| Migration ordering | `hr_documents` (migration 15) is created after several tables that reference `hr_document_id` conceptually (`contracts`-adjacent `employee_positions` is migration 5, `leave_requests`/`mission_requests` are 12/13, `employee_salaries`/`loans` are 22/23) but none of those actually declare a real FK to `hr_documents` (see above), so there is no ordering *failure* today — the risk is purely that adding proper FKs later will require a migration-ordering rework or a deferred/alter-table approach. | P2 (informational) | Plan the FK addition (see `hr_document_id` row above) with this ordering constraint in mind — likely via a new migration that runs after all 27 existing ones, adding constraints with `Schema::table(...)->foreign(...)`. |

## 5. Domain Invariants

| Invariant | Current Enforcement | Required Enforcement | Priority |
|---|---|---|---|
| Exactly one current salary per employee (`EmployeeSalary.is_current`) | Application-level only (not even that — no application code enforces it either; it's simply unenforced) | Both (DB unique-key trick + service-layer transactional flip) | P0 |
| Exactly one current/primary position per employee (`EmployeePosition`) | Missing entirely | Both | P0 |
| Exactly one active contract per employee | Missing entirely | Both | P0 |
| No overlapping leave requests per employee | Missing entirely | Application-level (transactional range check with row lock); DB-level exclusion constraints are not portably assumed for this package's target RDBMS set, so this must be Application-level at minimum | P0 |
| No overlapping mission requests per employee | Missing entirely | Application-level | P1 |
| No duplicate attendance per employee per day | **Database-enforced** (`unique(['employee_id','date'])`) | Already satisfied — keep as-is | — (done) |
| Unique employee code | Database-enforced (`employees.employee_code` unique), but **generation** is racy (see Concurrency file) | Both — DB constraint already correct; needs a concurrency-safe generator so the constraint isn't relied upon as the *only* line of defense (currently a violation surfaces as an unhandled exception to the end user) | P0 |
| Unique document number | Database-enforced (`documents.document_number` unique), but **generation** is racy (same class of issue as employee code) | Both — same reasoning | P0 |
| Payroll cannot change after closing/locking | Application-level only, and only partially: `PayrollPeriodStatus::canEdit()` exists as a helper (`src/Enums/PayrollPeriodStatus.php:48-51`) but is **never called** by any code, since no `PayrollService` exists yet | Both (service must check `canEdit()` before any mutation; DB should reject writes to a locked period's records via an app-level guard at minimum, ideally a DB trigger or a check in a repository-style write path) | P0 |
| Approved documents cannot be edited | **Application-level, and working**: `HrDocument::ensureEditable()`/`canEdit()` correctly restrict edits to `Draft` status (`src/Models/HrDocument.php:65-77`, `src/Enums/DocumentStatus.php:35-38`) | Already Both-equivalent in intent (no DB constraint, but the single write path — the model itself — enforces it consistently); acceptable as Application-level given there's only one way to mutate a document today | — (acceptable as-is, revisit if a second write path is ever added) |
| Rejected documents cannot be approved | Application-level, and **partially broken**: `approve()` only checks `$approval->status !== Pending` (`src/Services/DocumentService.php:101-103`) on the *approval* row, not the parent document's status — so an approver whose step is still `Pending` can call `approve()` even after the document itself has already been set to `Rejected` by a different step's `reject()` call. | Application-level fix: `approve()`/`reject()` must check the parent `HrDocument.status` is still `Pending` before acting, not just the individual approval row's status. | P0 |
| Loan cannot exceed configured limits (`max_amount`, `max_percentage_of_salary`, `max_active_loans`) | Missing entirely | Application-level (no plausible DB-level check across salary/loan tables) | P1 |
| Payroll cannot be calculated twice incorrectly (idempotent recalculation) | Missing entirely (no calculation code exists to be idempotent or not) | Application-level, designed in from the start of the calculation engine — see Concurrency file | P0 |
| Leave balance cannot go negative | Missing entirely | Application-level (validated before request creation and before approval-time decrement) | P0 |
| Workflow step `assigned_to` is always a valid, resolvable approver before an approval row is created | Missing entirely — currently the opposite is true: unresolved `approver_type`s produce a `NULL` `assigned_to` attempt against a `NOT NULL` column | Application-level (resolve `approver_type` → concrete user id *before* attempting the insert; fail the submission with a clear domain exception if unresolvable, rather than letting a DB constraint violation bubble up) | P0 |
